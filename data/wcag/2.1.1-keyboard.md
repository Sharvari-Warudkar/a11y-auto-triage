# WCAG 2.1 Success Criterion 2.1.1: Keyboard (Level A)

## Requirement
All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes, except where the underlying function requires input that depends on the path of the user's movement and not just the endpoints.

## Who is affected
- Users with mobility impairments who cannot use a mouse
- Blind users who rely on keyboard navigation with screen readers
- Users with tremors who use keyboard instead of mouse
- Power users and developers who prefer keyboard navigation

## Common failures
- onClick handlers on non-interactive elements (divs, spans) without keyboard equivalents
- Dropdown menus that only open on mouse hover
- Drag-and-drop functionality without keyboard alternative
- Custom components built with divs that don't respond to Enter/Space
- Infinite scroll that cannot be navigated with keyboard

## Sufficient techniques
- H91: Using HTML form controls and links
- G202: Ensuring keyboard control for all functionality
- SCR20: Using both keyboard and other device-specific functions

## Remediation
1. Use native interactive HTML elements (button, a, input) instead of styled divs
2. If custom elements must be used, add tabindex="0" and keyboard event handlers
3. Ensure all hover interactions have keyboard-equivalent triggers
4. Test by unplugging your mouse and navigating the entire page with Tab, Enter, Space, Arrow keys
5. Provide skip links for repeated navigation blocks
