A11Y Auto-Triage: AI-Powered WCAG AA Violation Detection & Bug Logging

Author: Sharvari Warudkar | Role: QA Engineer, Perficient | Case: L1_Case05_Open_Choice_Prototype | Date: August 2026

Competencies: Spec-Driven Development Context Engineering AI Output Review RAG Pipeline

1. Problem Statement

Domain: E-commerce — accessibility compliance

User: QA engineers responsible for accessibility testing on e-commerce platforms

Problem: Manual WCAG 2.1 AA audits are slow (~45 minutes per page), inconsistent across engineers, and produce bug reports that lack remediation guidance. Developers receive vague tickets and spend additional time asking follow-up questions, doubling the fix cycle.

Definition of Success: Reduce per-page triage from ~45 min to <5 min, with ≥90% correct WCAG criterion citations and code-level fix suggestions that developers can act on without follow-up questions.

2. Solution Overview

An automated pipeline that scans web pages for WCAG 2.1 AA violations using industry-standard tools, retrieves relevant WCAG success criteria from a local knowledge base, and generates structured bug reports using AI — ready for Jira.

Architecture

Target URL → Playwright + axe-core (scan) → Deduplication → RAG Retrieval (WCAG docs) → LLM Generation (Groq/Llama 3.3) → Structured JSON Bug Reports

3. Data Provenance

Source: Synthetic HTML fixtures simulating common e-commerce pages (product listing, product detail, cart, checkout) with deliberately injected WCAG AA violations. All fixtures authored by the submitter based on real violation patterns observed in production e-commerce sites.

WCAG Knowledge Base: 9 WCAG 2.1 success criteria (Level A and AA) manually curated as markdown files covering the most common e-commerce violations.

What it does NOT represent: Dynamic SPA rendering, third-party widget violations, mobile-specific touch-target failures, or violations that appear only after user interaction.

Sensitive data: No real user data, no production URLs, no proprietary code. All content is original synthetic material.

6. RAG Pipeline

StageImplementation
LoadRead 9 WCAG markdown files from data/wcag/
ChunkOne chunk per success criterion (title + requirements + techniques + remediation)
IndexKeyword/TF-IDF frequency maps per document
StoreJSON persistence at data/vector-store.json
QueryCosine similarity on keyword vectors → top-3 per violation

Chunking trade-off: One-doc-per-criterion keeps context complete but means borderline violations (e.g., placeholder contrast vs. missing label) can match the wrong criterion when keywords overlap. Pre-filtering by axe-core rule tags improves accuracy from 80% → 93%.
